# svcdesk - Service Desk API Specification

## Purpose

The svcdesk service provides a REST API for managing service desk tickets.

The service must provide predictable ticket creation, priority calculation,
ticket state transitions, SLA calculation and validation of incoming requests.
The API is intended to provide a consistent interface for service desk agents,
monitoring systems and future integrations.

## Health

The service shall expose a health endpoint.

`GET /health` shall return HTTP 200 when the service is running and ready
to accept requests.

The health response shall identify the service as `svcdesk`.

## Tickets

The service shall allow clients to create and manage service desk tickets.

Each ticket shall have a unique identifier generated by the service.
A ticket shall contain a title, optional description, reporter information,
impact, urgency, calculated priority, current state and SLA information.

The reporter information shall contain a name and may contain an e-mail
address and VIP flag.

Impact and urgency shall use values from 1 to 3.

Invalid input shall be rejected with an appropriate HTTP error response.

The service shall allow clients to retrieve a single ticket and list existing
tickets. Ticket lists may be filtered by state and priority.

## Priority

Ticket priority shall be calculated from impact and urgency according to the
service desk priority matrix.

The priority calculation shall produce one of the following values:

- P1
- P2
- P3
- P4

The calculation shall be deterministic for the same ticket data.

Priority is controlled by the service. A priority value supplied by the client
shall not override the priority calculated by the service.

The service shall also support tickets reported by VIP users according to
the selected VIP priority rule documented in `DECISIONS.md`.

## Ticket state

Tickets shall follow the following state model:

`new -> acknowledged -> in_progress -> resolved -> closed`

Only valid state transitions shall be accepted.

The service shall provide separate actions for acknowledging, starting,
resolving and closing a ticket.

Invalid state transitions shall be rejected with an appropriate HTTP error.

The service shall also provide a reopen operation. The behaviour for reopening
resolved and closed tickets shall follow the selected policy documented in
`DECISIONS.md`.

The reopen operation shall respect the required seven-day reopening window.

## SLA

The service shall calculate acknowledgement and resolution SLA targets
according to ticket priority.

The SLA implementation shall support both wall-clock and business-hours
calculations where required.

Business hours are Monday to Friday from 08:00 to 16:00 in the
`Europe/Warsaw` time zone.

The service shall expose SLA information including:

- acknowledgement due time,
- resolution due time,
- acknowledgement breach status,
- resolution breach status,
- SLA paused status.

The service shall correctly determine whether an acknowledgement or resolution
target has been breached.

The service shall support the test clock provided by the laboratory environment
so that SLA behaviour can be tested deterministically.

When test-clock support is enabled, the `X-Test-Clock` request header shall be
used as the current time for that request.

## Validation and errors

Requests containing invalid required data shall be rejected.

This includes invalid titles, impact values, urgency values and malformed test
clock values.

Unknown ticket identifiers shall return HTTP 404.

Invalid ticket state transitions shall return HTTP 409.

Error responses shall contain a JSON `error` object.

Fields controlled by the service and unknown request fields shall not override
the values calculated and maintained by the service.

## Conflicting requirements

The requirements contain three conflicts for which one admissible behaviour
must be selected.

### C1 - SLA clock behaviour for P1 tickets

The implementation shall use the `wallclock` behaviour.

P1 acknowledgement and resolution targets therefore run continuously.
P2, P3 and P4 targets use the business-hours clock.

### C2 - Closed tickets and reopening

The implementation shall use the `immutable` behaviour.

Resolved tickets may be reopened within the allowed seven-day window.
Closed tickets cannot be reopened and further work requires a new ticket.

### C3 - VIP reporters and the priority matrix

The implementation shall use the `vip` behaviour.

The normal impact and urgency matrix is applied first. If a VIP ticket would
have priority P3 or P4, its priority shall be raised to P2. P1 and P2
priorities remain unchanged.

The selected C1, C2 and C3 behaviours and their justification shall also be
documented in `DECISIONS.md`. The declared decisions must match the behaviour
implemented by the running service.

## Persistence

Ticket data shall be stored persistently so that tickets can survive a restart
of the service container.

A Docker named volume may be used to store persistent application data.

## Runtime

The service shall run using Docker Compose.

Docker Compose shall define a service named exactly `svcdesk`.

The service shall listen on port 8080 inside the container.

The environment variable `SVCDESK_TEST_CLOCK` shall be enabled for the
laboratory environment.

The application shall provide all required dependencies inside the built
container and shall not require external network access at runtime.

The Docker Compose configuration shall not use host-path bind mounts.
